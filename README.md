# Emacs config

Literate Emacs configuration. `conf.org` is the source of truth; everything else
is either a loader or an archived version.

| File                                | Role                                                                       |
|-------------------------------------|----------------------------------------------------------------------------|
| `init.el`                           | Loader. Sets `vc-follow-symlinks`, then tangles + loads `conf.org`.        |
| `conf.org`                          | The actual config. **Edit this one.**                                      |
| `conf.el`                           | Generated by tangling `conf.org`. Do not edit; regenerated on every start. |
| `init-master.el`, `conf-master.org` | Archived older config, not loaded.                                         |
| `conf-dot-el-from-lost-conf.org`    | Archived recovery artifact, not loaded.                                    |
| `.emacs~`                           | Archived, not loaded.                                                      |

Tested on GNU Emacs 31.1, Ubuntu (Linux 7.0.0).

## Setup

### 1. Symlinks

Emacs reads `~/.emacs.d/`, so link the three files it needs into place:

```bash
ln -s /home/scott/code/emacs/init.el   ~/.emacs.d/init.el
ln -s /home/scott/code/emacs/conf.org  ~/.emacs.d/conf.org
ln -s /home/scott/code/emacs/conf.el   ~/.emacs.d/conf.el
```

The third one is not optional and is easy to miss. `init.el` sets
`vc-follow-symlinks t`, so when Org visits `~/.emacs.d/conf.org` it resolves the
symlink and writes the tangled output to `/home/scott/code/emacs/conf.el` — but
`org-babel-load-file` then tries to load `~/.emacs.d/conf.el`. Without the link
you get:

```
Cannot open load file: No such file or directory, /home/scott/.emacs.d/conf.el
```

The link is dangling until the first tangle, which happens before the load, so a
fresh machine works fine.

Not linked, by design: `custom-vars.el` (set as `custom-file` in `conf.org`) is
generated per-machine and stays local to `~/.emacs.d/`.

### 2. System packages

```bash
sudo apt install fonts-jetbrains-mono   # conf.org set-frame-font; errors out the config if missing
sudo apt install cmake libtool libtool-bin   # vterm builds a native module
                                             # (or libvterm-dev, see below)
sudo apt install racket                 # to execute org racket src blocks
sudo apt install sbcl                   # sly (Common Lisp)
sudo apt install sqlite3                # org-roam database
```

`fonts-jetbrains-mono` is the one that breaks startup rather than degrading it:
`set-frame-font` signals an error on a missing family, which aborts the rest of
the config load.

### 3. Manually cloned packages

`ob-racket` is not on MELPA or GNU ELPA, so `:ensure` cannot fetch it. It is
loaded from a local checkout via `:load-path`:

```bash
mkdir -p ~/code/outside
git clone --depth 1 https://github.com/hasu/emacs-ob-racket ~/code/outside/emacs-ob-racket
```

If this is missing, `org-babel-do-load-languages` hits `(racket . t)` and fails
with `Cannot open load file: No such file or directory, ob-racket`.

### 4. Inside Emacs, after first start

```
M-x all-the-icons-install-fonts
M-x nerd-icons-install-fonts
```

Both are needed, and they are not interchangeable. `conf.org` uses
`all-the-icons` directly, while `doom-modeline` v4+ renders its glyphs through
`nerd-icons`, which needs Symbols Nerd Font Mono (`NFM.ttf`). Without them the
modeline shows boxed hex codepoints.

A boxed code in the `F0000`–`F1AF0` range (e.g. `0F0CE4`) is a Nerd Font glyph,
so it is `nerd-icons-install-fonts` that's missing; the all-the-icons glyphs sit
in a different range. Check coverage for a specific codepoint with:

```bash
fc-list ':charset=f0ce4' family
```

Restart Emacs after installing — font sets are cached at startup.

### 5. Directories the config expects

```bash
mkdir -p ~/Documents/repos/roam   # org-roam-directory
```

Miniconda at `~/miniconda3` is hardcoded as `conda-anaconda-home`; adjust
`conf.org` if it lives elsewhere.

## Troubleshooting

### `Cannot load <package>` for a package that is clearly installed

If the config aborts partway through startup (any of the errors above), package.el
can leave a package half-installed: source files downloaded, but the byte-compile
and autoload-generation step never ran. `package-activate` then fails and
`use-package` reports `Cannot load <package>`.

A healthy package directory under `~/.emacs.d/elpa/` contains `.elc` files and a
`<name>-autoloads.el`. A broken one has only `<name>.el` and `<name>-pkg.el`.
Find them all:

```bash
cd ~/.emacs.d/elpa && for d in */; do d=${d%/}; \
  ls "$d"/*autoloads.el >/dev/null 2>&1 || echo "NO AUTOLOADS: $d"; done
```

Ignore `archives` and `gnupg` — they aren't packages. Delete any others and
restart; package.el reinstalls them cleanly.

If a package keeps coming back half-installed, reinstall it from a separate
batch Emacs instead. That process is independent of the startup that keeps
failing, so it runs to completion:

```bash
rm -rf ~/.emacs.d/elpa/<package>-<version>
emacs -Q --batch --eval '(progn
  (setq package-user-dir "~/.emacs.d/elpa")
  (require (quote package))
  (setq package-archives (quote (("melpa" . "https://melpa.org/packages/")
                                 ("elpa"  . "https://elpa.gnu.org/packages/"))))
  (package-initialize)
  (unless package-archive-contents (package-refresh-contents))
  (package-install (quote <package>)))'
```

A completed install leaves `<name>-autoloads.el`, `<name>.elc` and usually
`README-elpa`. Only `<name>.el` plus `<name>-pkg.el` means it was cut short.

### Theme loads but the frame keeps default colors

`desktop-save-mode` saves explicit `foreground-color` / `background-color` frame
parameters and restores them from `after-init-hook` — after `conf.org` has
already run `load-theme`. The theme ends up enabled but painted over. Check with
`M-: custom-enabled-themes`: if it lists the theme, this is what's happening.

Fixed here by `(setq desktop-restore-frames nil)`, which keeps buffer restore
and drops frame-parameter restore. If colors are ever wrong again after changing
themes, delete `~/.emacs.d/.emacs.desktop` to clear stale saved parameters.

### A file opens in the wrong major mode after adding a new mode package

`desktop-save-mode` records each buffer's major mode at save time and restores
that mode directly, bypassing `auto-mode-alist`. A file that was open before the
mode package existed keeps coming back in its old mode — typically
`fundamental-mode` — no matter what `use-package :mode` says.

It self-heals: set the mode with `M-x <mode>`, and the next desktop save records
the right one. To clear all stale state at once, delete
`~/.emacs.d/.emacs.desktop`. Files not listed in the desktop file were never
affected and always used `auto-mode-alist`.

### vterm: `Cannot open load file ... vterm-module`

The Lisp half installed but the native module didn't build. Run the build by
hand to see why:

```bash
cd ~/.emacs.d/elpa/vterm-*/build && cmake .. && make
```

`libtool not found` means cmake fell back to compiling a bundled libvterm and
needs libtool to do it. Either fix works:

- `libtool libtool-bin` — cmake builds the bundled libvterm. This is what this
  machine uses, and it produced a working `vterm-module.so`.
- `libvterm-dev` — cmake finds the system libvterm and skips the bundled build.

Afterwards `rm -rf` the `build` directory before retrying: `CMakeCache.txt`
caches the failed probe and will keep reporting libvterm as missing.

## Notes

- `conf.el` is generated and currently untracked; consider adding it to
  `.gitignore`.
- `use-package-always-ensure` is `t`, so any package not on an archive needs an
  explicit `:ensure nil` alongside its `:load-path` (see `ob-racket`).
- `doom-font` is set in `conf.org`, but that variable belongs to Doom Emacs.
  This is vanilla Emacs using only `doom-themes`, so the font actually comes
  from the `set-frame-font` call.
- The first block in `conf.org` exists only to tangle the `lexical-binding`
  cookie onto line 1 of `conf.el`. Keep it first — the cookie is ignored
  anywhere else.
- `doom-theme` and `doom-font` are set in the Doom stuff block but belong to
  Doom Emacs core, not the `doom-themes` package. They do nothing here; the
  active theme comes from the `load-theme` call in the ef-themes block.
- If `highlight-indent-guides cannot auto set faces` appears at startup, the
  package couldn't derive guide colors from the `default` face. Uncomment the
  three `set-face-*` lines in the indent highlights block to set them directly.
- `global-display-line-numbers-mode` is enabled twice, in the Preliminaries
  block and again in the Line numbering block. Harmless, but only one is needed.
- Neither straight.el nor elpaca is bootstrapped. Package management is
  package.el + `use-package`. Recipe keywords like `:elpaca` silently do
  nothing here.
